# chase-farm — 黑白棋训练数据生成农场

用 Edax 在机房批量生成带标签的黑白棋局面, 供 chase 项目的监督训练使用。
**纯标准库 Python 3.6+, 无需 pip 安装任何东西。**

---

## 快速开始(机房)

```bash
# 第一次: 拉代码
cd ~ && git clone https://github.com/joewang0430/chase-farm.git
cd chase-farm

# 自检(不起工人) —— 第一台机器会自动编译引擎并验收, 约 1 分钟
./bootstrap.sh --check

# 起工人(默认 核数-4 个)
./bootstrap.sh

# 看进度(任意机器上都能看全场)
./bootstrap.sh --status

# 全场收工(所有机器的工人下一局结束后干净退出)
./bootstrap.sh --stop
```

因为家目录是 NFS 共享的, `~/chase_farm/` 对全机房所有机器是**同一个目录**:
引擎只需第一台编译一次, 开局池只生成一次, 所有机器的分片都落到同一处, STOP 文件全场可见。

## 一键铺开到多台

在中枢机(如 p107)上:

```bash
# 先配一次免密(NFS 共享 ~/.ssh, 配一次全场生效)
ssh-keygen -t ed25519 -N ''
cat ~/.ssh/id_ed25519.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

# 起全场
for i in $(seq 97 132); do
  ssh -o StrictHostKeyChecking=no p$i \
    'cd ~/chase-farm && ./bootstrap.sh' </dev/null &
done
wait

# 收工(一条命令全场生效, 不需要挨台登录)
./bootstrap.sh --stop
```

## 目录结构(运行时)

```
~/chase_farm/                共享根目录
  engine/lEdax               自己编译的 Edax(全场共用)
  engine/data/eval.dat       权重(随仓库带来, sha256 校验)
  edax-reversi/              Edax 源码(钉死在验证过的 commit)
  openings8.jsonl            8手开局池, 67k 条(全场共用)
  shards/                    数据分片 <主机>_<时间戳>_<pid>_<序号>.jsonl
  logs/                      每个工人的 stderr
  STOP                       此文件存在 = 全场收工信号
```

## 数据格式

每行一个局面:

```json
{"pcs":24,"my":"1234567","opp":"8901234","best":"f5","score":-2,"g":17,
 "src":"p107_0829123456_31363","T":6.0,"Tsched":"6","L":15,"SL":5}
```

| 字段 | 含义 |
|---|---|
| `pcs` | 盘上子数(只记录 12~53, 与训练分桶 12-25/26-39/40-53 对齐) |
| `my` / `opp` | 位棋盘, **十进制字符串**(避免 JSON 大整数精度问题) |
| `best` | 老师认定的最优着法 |
| `score` | 老师的评分, 净胜子, **轮到方视角** |
| `g` | 该工人的第几盘 |
| `src` | 主机_启动时间戳_进程号, 用于溯源与去重 |
| `T` | 该局面**实际用于抽样的温度**; `0` = 已走出随机段, 走的是确定性 top-1 |
| `Tsched` | 温度策略原文(`"6"` 或 `"6/5/4"`) |
| `L` / `SL` | 老师档位 / 选择器档位 |

## 生成方案

1. **前 8 手**: 从对称去重的**全枚举**开局池(67,361 条)随机取一条 —— 开局空间 100% 覆盖, 零采样偏差。
2. **随机段**: 从 `{12,13,...,53}` 抽一个终点 pcs, 段内双方按温度 `softmax(score/T)` 抽样落子。
   随机段长度本身是随机的 —— 短段产出接近正常对局的局面, 长段产出畸形残局, 整个可达空间被均匀采到。
3. **随机段之后**: 双方**全程走老师的最优着法**直到 pcs=53。
4. **标签**: 每个局面都记老师的最优着法 + 评分, **与实际走了哪一步无关**。
   走偏只是为了**到达**更多样的局面, 教材永远是正解。

## 双引擎分工

| 角色 | 引擎 | 职责 |
|---|---|---|
| **老师** | Edax **L21** + `hint 1` | 出标签(best + score), 每个局面都问 |
| **选择器** | Edax **L5** + `hint 30` | 只决定随机段"下一步走哪", **评分绝不进标签** |

为什么拆开: `hint 30`(要整张评分表)比 `hint 1` 贵得多, 而温度采样只需要一张大致靠谱的表。
标签始终来自老师, 所以选择器用低档位不影响数据质量。实测选择器只占总耗时的 **3~13%**。

## 温度: 统一 T=6

实测(L5 引擎, 每组 200~800 盘, 统计"24+ 子一边倒局面"的占比):

| 温度 | 盘数 | 24+占比 | 角落独占(上风) |
|---|---|---|---|
| T=4 | 202 | 19.5% | 21.2% |
| T=5 | 205 | 18.9% | 21.5% |
| **T=6** | **800** | **19.7%** | **22.2%** |
| T=8 | 200 | 22.8% | 24.1% |
| T=∞(纯随机) | 200 | **32.3%** | 29.7% |
| 6/5/4 分段 | 400 | 19.1% | 20.0% |

两条结论:
- **温度确实有用** —— T=∞ 明显跑出其余各组(24+ 从 ~20% 涨到 32.3%)。
- **T=4~T=8 在这个样本量下分辨不出来** —— T=6 自己四次重复的跨度就有 15.9%~23.3%,
  比组间差距还大。分段温度 6/5/4 与统一 6 打平, 无可测量收益, 故不采用。
  (代码保留分段能力: `--temperature 6/5/4`, 想再测随时可用。)

## 老师档位: Edax L21

900 题实测(对照 Othello Sensei 标注, 四个档位跑同一批题):

| 档位 | 合计 top1 一致 | early | mid | late | 用时 |
|---|---|---|---|---|---|
| L12 | 86.3% | 82.7% | 76.3% | 100.0% | 443s |
| L13 | 88.9% | 82.3% | 84.3% | 100.0% | 570s |
| L14 | 89.0% | 84.7% | 82.3% | 100.0% | 484s |
| **L15** | **90.2%** | **86.0%** | **84.7%** | **100.0%** | **388s** |

这四档里 L15 质量最高且总耗时最短。但**再往上还有肉** —— 与 L21 按段对齐:

| 段 | L15 top1 | L21 top1 | L15 符号 | L21 符号 |
|---|---|---|---|---|
| early | 81.3% | **88.0%** | 93.3% | **95.9%** |
| mid | 80.3% | **87.8%** | 93.9% | **97.1%** |
| late | 100.0% | 100.0% | 97.2% | 97.2% |

early/mid 各涨 6.7 / 7.5 个点, 符号涨 2.6 / 3.2 个点 —— 正好落在网络最难学的两段。
late 段两者完全相同(精确求解, 档位不起作用, L12 就已经 100%)。

> **口径陷阱**: 历史日志里 "L21 合计 87.9% vs L15 87.2%" 看着只差 0.7 点, 是因为
> L21 那次 late 段 300 题**全部解析失败、没进分母** —— 等于拿 L21 的 early+mid
> 去比 L15 的三段全含。补上 late 后 L21 合计 92.2%, 比 L15 高 5.0 个点。

**成本**: 同一批随机段局面实测, 整局 L15 12.2s / L18 49.8s / L21 46.8s(L21 约 L15 的 3.8 倍)。
机房 24 工人实测 L15 约 26 万局面/小时, 换 L21 约 6.8 万/小时 —— 仍远超需求, 故选 L21。

**曾经的坑**: L21 在 late 段历史上出现过 300/300 解析失败。本版驱动专项复测
(pcs 40-53, 每档 10 个随机段局面)**0/140 失败**, 已排除。

**为什么是 Edax 不是 Egaroucid**: 质量同级(Egaroucid L15 在另一批 900 题上 89.2%),
但在**农场真正要标的随机段局面**上, 同一批 28 个局面逐格对照, 整局 Edax 8.7 秒 vs Egaroucid 351 秒。
Egaroucid 在畸形局面上退化严重(正常局面 0.27s/局面 → 随机段 8.4s/局面), Edax 几乎不受影响。

## 成本

机房 p107 单工人实测(L15): **5.5 秒/盘**; 本机 Mac 34 秒/盘。
本机 L15 单工人 10 盘的分部门拆解:

| 部门 | 占比 |
|---|---|
| 老师 hint(引擎搜索) | ~87% |
| 选择器 hint | ~13% |
| setboard | <2% |
| 读取 / 解析 / 对局逻辑 / 落盘 | ~0% |

其中 **pcs 37~41 这 5 手吃掉老师开销的 66%** —— Edax 在空格数 23~27 时会切进近乎精确的深搜。
这是引擎的固有行为, 要动就得牺牲标签质量, 故不动。

单盘耗时波动很大(样本 42~160 秒), 盘数少时的数字不可信。
**机房的真实吞吐必须在机房实测**(见下)。

## 引擎: 自己编译 + 强制验收

`bootstrap.sh` 会 clone Edax 源码并编译。三件事值得知道:

1. **不用官方 Makefile**。它的 gcc 优化档写死了 `-flto=auto`(需 gcc≥10)和 `ARCH=x86-64-v3`(需 gcc≥11),
   而机房是 gcc 8.5, 两者都不认。改用 Edax 的 `all.c` 单文件合并版, 一条 gcc 命令编完。
2. **钉死在验证过的 commit**, 不用 `v4.6` tag —— 该 tag 的源码启动即
   `hash_init: cannot allocate the hash table` 后卡死(本机实测)。
3. **编译成功 ≠ 答案正确**。`eval.dat` 版本不符、编译参数不当、CPU 指令集不匹配, 都可能让引擎
   跑得起来但答错, 那样的数据事后极难发现。所以编译完必须过
   [`verify_engine.py`](verify_engine.py) 的 40 条标准答案(`best` 与 `score` 逐字段相等),
   不过就中止, 绝不生成数据。

## 正确性自检

```bash
python3 selftest.py --engine ~/chase_farm/engine/lEdax --openings ~/chase_farm/openings8.jsonl --games 10
```

它不"读代码看对不对", 而是**从产出的数据反推**, 检查五件只有实现正确才可能成立的事:

| 检验 | 内容 | 能抓住什么 |
|---|---|---|
| 1 | 相邻两条记录的盘面之间恰好隔一步合法着法 | 盘面/视角/换边错误 |
| 2 | 凡 `T=0` 的记录, 复原出的那一步必须等于 `best` | 误把选择器的着法用在确定段 |
| 3 | `T>0` 的记录里实走 ≠ `best` 的比例在 (0,1) 之间 | 选择器没生效 / 温度没生效 |
| 4 | 抽样记录用**独立新起的 L15 引擎**重问, `best`/`score` 逐字段相等 | 标签被选择器(L5)污染 |
| 5 | `pcs` 在 [12,53]; `T` 与阶段一致; `L`/`SL` 与命令行一致 | 字段错乱 |

## 并发: 开满

p107(28核/31GB)实测并发曲线(L15, 每档 10 分钟):

| 工人数 | 局面/10分 | 实际倍数 | 每工人效率 | 边际(每新增1工人) |
|---|---|---|---|---|
| 1 | 4,606 | 1.0x | 100% | — |
| 4 | 17,678 | 3.8x | 96% | +4,357 |
| 12 | 27,918 | 6.1x | 51% | +1,280 |
| 24 | **43,176** | 9.4x | 39% | +1,271 |

单工人效率从 4 个之后腰斩, 但**边际收益在 4→12 与 12→24 之间是平的**(都约 1,270),
总产出一直在涨 —— 没有"超额订阅导致总吞吐下降"的拐点。故**默认开满 `核数-4`**。

每个工人 = **2 个 Edax 进程**(老师 + 选择器), 常驻约 165MB; 24 工人约 4GB, 内存不是瓶颈。

## 排障

| 症状 | 处理 |
|---|---|
| `--check` 说编译失败 | 报错里带了可直接复制的手动命令; `-march=native` 不认就换 `-march=haswell`, 再不行去掉 `-march` |
| `--check` 说引擎验收失败 | **不要绕过**。多半是 `eval.dat` 或编译参数问题, 这个引擎会产坏数据 |
| 工人起不来说"已有工人在跑" | `pkill -u $USER -f worker.py` 后重试 |
| 某台机器分片不增长 | `tail ~/chase_farm/logs/<主机>_w1.log`; 引擎失联时工人会先就地重试 3 次, 仍失败才重启引擎 |
| 想临时加/减工人 | `./bootstrap.sh --stop` 后 `./bootstrap.sh --workers N` |

**注意**: 工人以 `nice 10` 运行, 只吃空闲 CPU, 别人登录用机时会自动让路; 默认每台留 4 核不占。
